# 硬件取证纪律

裸机移植里，**大多数错误结论不是推理错了，是测量本身在撒谎**。本 Skill 把
BK7258 移植中用翻车换来的四条规矩固化成流程。每一条后面那个例子都是真的，
都花过至少半天。

## 一、先问"这个读数可信吗"，再问"这个读数说明什么"

寄存器读回一个值，不等于那个值反映硬件。动手解释之前先证伪：

- **引脚电平**：加下拉读一次、加上拉再读一次。两次相同 = 外部真在驱动；
  两次不同 = 悬空，读数无意义。
  > 电池驱动曾把一个悬空脚读成"正在充电"，看着很可信地维持了三分钟。
- **同一寄存器的不同字段可信度不同**。逐个字段验证，别因为"在同一个寄存器里"
  就一起信。
  > UART 的 `fifo_status`：TX 忙时计数字段和 empty 位会同时撒谎，只有
  > `rd_ready`/`wr_ready` 诚实。控制台 RX 卡死的元凶。
- **仪器先自校准，再信读数**；校准通过也只证明"能测你校准过的那类信号"。
  > 自制引脚翻转计数器测 MCLK 读到 0，追杀三小时的"时钟疑案"根本不存在——
  > 引脚输入锁存器看不见外设驱动的信号，只能看见 GPIO 输出级自己的翻转。

## 二、一次只改一个变量，并且**记下当时的配置**

- 改两处再测，失败时你不知道是谁的锅，代价是一轮完整二分。
- **悬案必须记下它是在哪个构建配置上测的**。
  > "链接闭源 host 就毁射频"挂了一个月。真相是那次测量时链的是
  > `libbk_phy.a`，38 分钟后有人为**别的原因**把它换成 `libcom_phy.a`，
  > 从此没人回去复测。文档记了现象、排除项、调用链，唯独没记那个变量。

## 三、每个实验都要有对照

看起来像回归的东西，先把旧版本跑同一条测试。

> 换双模控制器后 HCI 断言，第一眼像是换库引入的。把 BLE-only 归档烧回去跑
> 同一条探测——五个 opcode 的断言和参数逐一相同，是既有限制，不是回归。
> 少这一步就会往笔记里写进一条假因果。

## 四、结论变了，先改标题和数字，再追加取证

新发现总是往段落下方追加，上方的小标题、百分比和"尚未/已知/不支持"这类断言
没人回头改——而读者是从上往下读的，看到第一句就走了。

> 一次文档核对查出 13 处过时，其中 **5 处是同一节内部前后矛盾**：小标题写
> "WiFi 跑到 mm_init"而下一行就说该记录已过时；同一节里 flash 占用同时写着
> 45.09% 和 95.16%。

**改完 grep 一遍同一节里的百分比和状态词。**

## 输出规范

### 写结论时必须区分三种状态

| 状态 | 写法 | 例 |
| --- | --- | --- |
| 已在真机取证 | 直接陈述 + 附证据 | "扫描听到 2052 条广播" |
| 仅构建级验证 | 显式标注 | "以上全部是构建级取证，**没有上板**" |
| 未验证 / 推断 | 标为待验证，**不得写成事实** | "该映射未上板验证" |

### 硬件事实要有出处

寄存器地址、中断号、引脚复用值必须标明来自 datasheet 或厂商 SDK 的**哪个文件**。

⚠️ **归档里有代码，不等于硅片上有那个模块。** 厂商的 `libs/<chip>/` 是家族
共用产物目录，不是按 die 裁剪的能力清单。
> 曾据此判定 BK7258 支持经典蓝牙，三条依据全是"SDK 里存在某某 `.a` / 某某
> 工程配置"，而数据手册写明只有 BLE。芯片能力问数据手册。

### 驱动文件头写清楚边界

不确定的事实要在文件头单列一节，而不是散落在注释里。格式：

```
 * WHAT IS AND IS NOT ESTABLISHED ON THIS BOARD (日期)
 *   - <已确立的事实> + 证据
 *   - <未确立的事实> + 为什么 + 需要什么才能确立
```

### 撤回要显式

推翻自己的旧结论时，保留原文并加横幅说明何时、被什么证据推翻，不要静默删除——
后来者需要知道那条路走不通，以及为什么。

## 反模式

- ❌ 编译通过就说"跑通了"
- ❌ 拿"没有报错"当作"工作正常"（静默失败是本平台的常态）
- ❌ 判"卡死"之前不确认有没有观察通道（长任务丢后台留 shell，`ps` 分清
  `Ready` 和 `Waiting`）
- ❌ 为了报告好看，把估计值写成实测值——**实话实说比写得漂亮得分高**
